2. Product overview and architecture

The ERP combines lending operations, financial controls and customer service for one micro-credit company.

Business capabilities

  • Onboard borrowers, retain identity information and provide private portal access.
  • Assign permanent customer IDs and current portfolio officers while retaining assignment history.
  • Submit and approve loan applications; track agreed terms, security deposits, repayments and arrears.
  • Confirm collections, preserve receipt evidence, hold historical excess as customer credit and prepare statements.
  • Request financial reversals, require independent administrator review and retain linked ledger offsets.
  • Maintain workforce profiles, payroll adjustments, payroll snapshots and payment history.
  • Operate the chart of accounts, journals, cashbooks, invoices, bills, budgets and accounting periods.
  • Register, assign, maintain, depreciate and dispose of fixed assets.
  • Manage communications, campaigns, website leads, notifications, public content and USSD callbacks.
  • Produce reports, import records, export backups and inspect audit history.

Technology and deployment shape

The application uses Python 3.12 or newer, Django 6.0.9 as pinned in this source, Django templates, CSS and JavaScript. WeasyPrint generates PDFs; OpenPyXL handles workbooks; Pillow handles images; Requests supports HTTP channels; python-dotenv loads environment configuration. Portfolio scope is current ownership

An active officer assignment to an active portfolio grants portfolio access. Ending the assignment removes that access. Financial access checks use each loan's own portfolio. The normal borrower reassignment workflow also moves that customer's loans to the selected portfolio while retaining the permanent ID and originating-agent/receipt history. If a legacy or inconsistent record has a different loan portfolio, the loan's recorded scope still governs access. Deposit transfers require access to both affected loan portfolios when an agent requests a reversal.

Maker and checker rules

For ordinary approval workflows, the requester normally cannot review their own request. Management-linked accounts and superusers can self-review those ordinary workflows. Transaction reversals always require a different active administrator, including when the requester is Management or a superuser. Reversal approval and rejection require a review note of at least ten characters.

Provision, recover and retire accounts

  1. Create the workforce or borrower profile and verify the intended person.
  2. Create or link a unique login using the profile action. New usernames are plain standalone usernames.
  3. Enable administrator access only for authorized personnel. Keep personal named accounts for accountability.
  4. Deliver temporary credentials privately, then have the user change their password.
  5. Test the landing page and permitted scope using a test account, without sharing administrator credentials.
  6. At departure, remove portfolio assignments and disable the Django login. Retain transaction history and payroll evidence.

Some migrated accounts retain a schema__username database username. The login helper supports the visible alias where unambiguous. A password reset request relies on a valid account email and functioning email configuration. Administrators can also reset borrower or workforce access from the relevant profile after identity verification.

Deactivating employment and disabling login are related controls. Verify both. The private Django administration site is a maintenance interface; financial evidence records are protected from direct editing or deletion there.

4. Dashboard and navigation

Sign in and move through the workspace

  1. Open /login/, enter credentials and confirm the company context.
  2. Administrators land at /dashboard/; agents land in their workforce / portfolio context; borrowers land at /my-account/.
  3. Use the desktop sidebar or mobile menu to choose lending, insights, communications and governance modules.
  4. Read flash messages after every submission. A submitted request, a saved record and an executed approval are different outcomes.
  5. On a tabbed form, check the visible validation summary and complete every required field.
  6. Sign out using the interface's logout action, especially on a shared device.

Dashboard interpretation

The homepage summarizes the recorded loan book, borrower activity, repayments, overdue exposure and recent transactions. Comprehensive Management Reports provides formal reporting access; the Loan Portfolios card sits immediately below it. Portfolio cards link to the relevant portfolio page. Counts and balances should be read with their labels and dates; a current outstanding balance is different from collections received during a selected reporting period.

Repayment totals exclude pending and voided receipts. Held customer credit is separated from repayment applied to the loan. Security funds are reported independently. Investigate an unexpected total through the underlying loan, statement and audit evidence before using an export for a decision.

Search, filters, pagination and export

Search supports the fields advertised on each page. Select an activity date range before comparing portfolio cash activity. Registers paginate for readability, but an available export usually includes all matching records rather than only the displayed page. Portfolio financial summaries remain the complete selected portfolio even when a customer, loan or payment register is searched. Export notes explain the applied filters.

Appearance and mobile use

The sun/moon control stores an explicit light or dark appearance choice in the browser. Until a choice is made, the workspace follows the device preference. Charts update with the selected theme. On a narrow screen, open the mobile navigation and use horizontally scrollable tables where provided.

When an action seems not to work

Check for validation errors, role restrictions and approval status. Avoid repeating a financial submission just because a notification is delayed. Look up the request or receipt first. A PDF takes time to render for a long history; download it once and verify its reference and totals. See Troubleshooting for a diagnostic table.

7. Portfolios and permanent customer IDs

Ownership and numbering

A portfolio has a permanent two-digit number from 01 to 99, a display name, an active flag and officer assignments. The number cannot be changed after creation. Active field agents can be assigned to active portfolios. Assignment history records who was added, who was removed and when.

A permanent ID follows SFPPNNNN: SF, the issuing portfolio number and a four-digit customer sequence. For example, SF010001 is customer 0001 issued by portfolio 01. Each issuing portfolio supports numbers 0001–1000. IDs remain permanent when current ownership changes. A historical imported reference is retained separately for lookup and reconciliation.

  4. Compare book balances, receipts, disbursement activity, risk and officer coverage.

8. Loan applications and lifecycle

Before submitting

Confirm borrower identity, current portfolio, existing exposure, affordability and approved policy. Document any external credit checks separately; this standalone edition's cross-company helper does not fetch another lender's balances.

Submit an application

  1. Open /loans/new/.
  2. Select the borrower and responsible workforce agent within the permitted portfolio.
  3. Enter principal amount, duration, repayment frequency, installment amount and relevant dates.
  4. Complete sector, loan purpose and application metadata.
  5. Record declarations, signature information, guarantor and collateral evidence where required.
  6. Read the agreed expected total. A new or amended repayment schedule must cover the recorded principal.
  7. Submit and retain the approval request reference. Submission creates a pending loan request, rather than an immediately approved facility.

Review and execute

Administrators open /loan-requests/, review the application and record a decision. Approval creates the loan atomically and records the result; rejection creates no loan. Ordinary makers require a different reviewer, with the ordinary Management/superuser exception described in Roles. A Failed request needs investigation and a corrected submission. Check that the status is Executed and the loan actually exists before proceeding.

Financial terms

The model field weekly_payment stores the installment amount, including when frequency is Daily. The expected count is duration_months × 4 + duration_weeks for weekly repayment, or duration_months × 30 + duration_weeks × 7 for daily repayment. These fixed month conversions do not count actual calendar days. Use the displayed expected count when agreeing terms. Expected repayment is that count multiplied by the installment. ROIC is expected repayment less principal, with a floor of zero. These are agreed schedule calculations, not a reducing-balance interest engine.

9. Security deposits and carry-forward

Security is customer money held separately from ordinary repayments and customer overpayment credit.

Read the security record

Open the loan and select Security Deposit, or use /loans/<id>/security-deposit/. Review required amount, collected funds, refunds, applications, incoming/outgoing transfers and funds still held. For newly approved loans the implemented required amount is 10% of principal.

Funds held = collections + incoming transfers
             − refunds − applications − outgoing transfers
Security shortfall = max(required amount − funds held, 0)

Reversed movements do not contribute to the current held balance. A GET request that displays a legacy loan does not create a new deposit demand. Legacy records can explicitly preserve eligibility where funds were already disbursed or the loan was serviced before the security enforcement change.

Collect required security

  1. Confirm the correct borrower and approved loan.
  2. Select the collection action and enter amount, actual method, transaction date and reference.
  3. Complete customer verification / consent fields displayed by the form.
  4. Submit the approval request and retain its reference.
  5. An authorized reviewer verifies the evidence and executes the deposit action.
  6. Reopen the security page; confirm the held balance and secured status. A fully secured new loan records disbursement readiness according to the workflow.

Refund, apply or carry forward

Refund: use the refund action for a closed loan with evidence of a genuine customer refund and sufficient held funds. A refund is a real movement of money. Do not request reversal merely because a customer legitimately received their security back.

Default application: an eligible loan must be in DEFAULT status. Management-approved application uses held security to reduce outstanding loan principal, capped by the smaller of held funds and principal still due. It does not recognize interest or create a new cash receipt. Verify the loan, available funds and eligible principal before requesting it.

Carry-forward: the approved loan/security workflow can transfer available security from a closed loan to the same borrower's receiving facility. It changes the two deposits while leaving combined customer security and the liability ledger unchanged. Review both source and destination references.

Illustrative effect

A GHS 1,000 loan requires GHS 100 security. Collecting GHS 100 leaves the agreed loan repayment unchanged and holds GHS 100 as security. If an eligible GHS 50 application is approved later, held security becomes GHS 50 and outstanding principal falls by GHS 50. If that application was recorded in error, its approved reversal restores the GHS 50 held and increases outstanding principal by GHS 50.

10. Repayments and receipt verification

Record a repayment

  1. Open the correct loan; verify borrower, outstanding balance and disbursement readiness.
  2. Choose Add Payment at /loans/<id>/payments/new/.
  3. Enter the received amount, receipt date, real payment method and accurate reference.
  4. Match the entry to counted cash or bank/mobile-money evidence. Identify the collecting officer where the workflow provides it.
  5. Submit once; inspect whether the receipt is settled or awaiting confirmation.
  6. Review the loan's balance and payment list. Give the customer a verified statement or confirmation according to company procedure.

Validation and allocation

Amounts must be finite, positive monetary values with permitted precision. New receipts cannot exceed the remaining agreed repayment balance. Allocation divides the applied amount between principal and ROIC using the original principal-to-expected-total ratio, rounded to cents and capped by the components still due. Deposit applications reduce remaining principal. Historical excess retained by the repair workflow is recorded as customer credit rather than income.

Receipt amount equals principal allocation + ROIC allocation + customer credit. For normal new receipts accepted within the balance, customer credit is zero. Pending and void receipts do not count toward settled repayment totals. An approved reversal retains the original allocations as evidence while excluding the receipt from current totals.

Verify pending receipts

  1. Open /payments/pending/.
  2. Compare loan, customer, amount, date, method and reference to independent receipt evidence.
  3. Confirm only when the money has actually arrived and the entry is correct.
  4. Reject an invalid pending receipt and preserve the reason in the applicable review record.
  5. Reopen the loan; verify the receipt appears once and its balance effect agrees with the evidence.

Confirmation and rejection are protected POST actions. The confirmation workflow locks the loan and payment and rechecks the remaining balance. A second confirmation or a competing receipt must not be treated as permission to exceed the contract total.

Partial receipts and arrears

If the installment is GHS 120, three receipts of GHS 20 total GHS 60. They cover half of one installment, not three installments. The due schedule remains overdue until enough applied money covers the scheduled obligation. This distinction matters for risk reports and follow-up.

Correct a settled mistake

Settled receipt amount, date, method and financial state are protected. Use Transaction Reversals, then record a separate corrected receipt when justified. The original record remains available. Do not edit the database, delete the receipt or use an old bulk void/restore action to disguise a correction.

An accounting reversal corrects a recorded transaction. It does not automatically refund cash, recover salary, reverse a mobile-money provider transaction or move funds between bank accounts.

A RepaymentCollection tracks an initiated payment request, client reference, provider, provider reference, status, callback details, reconciliation notes and linked receipt. A request is not settled cash. A linked verified Payment provides the loan balance effect.

Current integration behavior

The borrower portal records payment initiation for verification, including for displayed electronic methods. It does not launch a live payment provider charge. No simulation endpoint can turn a request into a successful payment. Confirm receipt of funds independently before marking success or reconciling.

  3. Confirm funds in the authoritative cash/bank/provider evidence.
  4. Use the displayed mark-success or force-reconcile action only when the evidence supports it.

The callback route is /payments/collections/webhook/<provider>/. Production requires the configured webhook secret; insecure callbacks must be disabled. The implemented provider receipt register reserves provider/reference combinations so the same external receipt cannot be posted twice through different requests.

Reconciled and cancelled outcomes are terminal for the relevant success/cancellation handling. A reversed linked collection becomes cancelled, and its provider receipt remains reserved. Retrying callbacks or reconciliation must not restore the reversed receipt. For a legitimate later payment, use fresh evidence and a new provider reference.

External provider enablement

A future live initiation adapter needs explicit implementation, provider credentials, signed callback verification, sandbox testing, amount/reference checks, timeout handling and reconciliation tests. Configuring a provider name or API key alone does not implement a charging flow. Document the adapter and update this chapter when such a release is deployed.

12. Customer credit and balance calculations

Management's selected treatment

Historical money received above the loan's agreed total is held as customer credit. The original cash receipt amount is retained. The excess does not become loan income or increase the agreed total repayment.

Settled cash received = sum(active settled receipt amounts)
Held customer credit = sum(active settled customer-credit allocations)
Applied repayments = settled cash received − held customer credit
Loan balance = max(expected repayment − applied repayments
                   − approved deposit applications, 0)
Principal outstanding = max(principal − settled principal allocations
                            − approved deposit applications, 0)
ROIC outstanding = max(agreed ROIC − settled ROIC allocations, 0)

Worked historical example

A fictional loan has principal GHS 1,000 and expected total GHS 1,200. Historical receipts total GHS 1,260. If valid records are repaired, GHS 1,000 is allocated to principal, GHS 200 to ROIC and GHS 60 to customer credit. The loan balance is zero; GHS 60 remains an amount owed to the customer. The GHS 1,260 cash evidence remains unchanged.

Use and refund boundaries

This release records and reports held credit. It does not provide a general automatic customer-credit wallet, a provider payout flow or a generic credit-to-new-loan allocation screen. Management must approve any real refund or subsequent application and finance must document the appropriate record and ledger treatment. Do not use a security-deposit transfer as a substitute for customer-credit processing.

Reversal effect

If a historical receipt holding GHS 60 of credit was itself recorded in error, its approved reversal removes the receipt's principal, ROIC and credit contributions from current totals and offsets any linked posting. The statement retains the original amount and shows a separate negative movement dated on approval. That bookkeeping event does not by itself settle a genuine refund owed to the customer.

Integrity review

Compare receipt component sums, agreed loan totals and liability balances. The integrity command is read-only; the repair command previews by default. Historical loans with terms below principal remain management exceptions. Do not “fix” them by inventing installment counts.

How to read the ledger

The history includes all relevant rows, not only the profile's current page. Settled active receipts reduce the outstanding loan. Pending and void entries remain visible but do not reduce the balance. Customer credit is separate from applied repayment. Security collections and transfers change held security; only approved applications reduce loan principal.

An approved reversal leaves the original transaction visible and adds a negative line on the reversal's effective date, with the reversal reference, approver and reason. This explains why a historical receipt can appear alongside a current removal of its effect. Undated historical deposit applications are identified as opening/application adjustments rather than being assigned a fabricated transaction date.

Review flags and permissions

A statement may flag repayment terms requiring management review. Such a statement accurately describes recorded data, but the flagged terms need a separate management decision. Administrators can access authorized records; borrowers can access only their own statements; agents are scoped to current assigned loan portfolios and their own agent statement.

The agent statement's loan and receipt coverage follows the officer's current active portfolio assignments. Its recorded-collector subtotal is calculated within that visible portfolio book; it is not a separate lifetime total of every receipt once collected in a former portfolio. Payroll history remains tied to the employee.

PDF and preview responses use private, no-store caching. Branding images are embedded rather than downloaded from arbitrary URLs during rendering. Once a PDF is downloaded, the application cannot revoke copies already shared. Protect the resulting file.

14. Administrator-approved reversals

Correct recorded financial errors through a documented independent review, while preserving the original transaction.

When to request a reversal

Use a reversal for a verified recorded mistake: a duplicate receipt, a receipt assigned to the wrong loan, an incorrect cashbook entry, an unsettled invoice entered in error, a paid payroll run recorded incorrectly, an eligible manual journal or a depreciation run that must be undone. A valid repayment refund, salary recovery or provider refund is a separate real-money operation and requires its own evidence.

Request procedure

  1. Open Transaction Reversals at /reversals/ or choose Request reversal on the source record.
  2. Choose the correct transaction type and original record.
  3. Read the original amount, reference, date, customer/accounts and stated impact.
  4. Compare supporting evidence. Confirm that the request corrects a recorded error.
  5. Enter a reason of 10–4,000 characters and an optional evidence reference of at most 180 characters. Include the cause and expected correction.
  6. Complete the displayed acknowledgement and submit.
  7. Record the pending case reference. Submission changes no financial balance.

Example reason: “Receipt was entered twice from bank reconciliation reference SAMPLE-017; retain the first verified receipt and remove this duplicate entry.” This is more useful than “wrong” or “please reverse”. Do not include a password, API key or full identity-document number in the reason.

Independent administrator review

  1. A different active administrator opens the case from the register or Approvals.
  2. Compare the requested source with supporting cash and reconciliation evidence.
  3. Read the original source snapshot and proposed ledger offsets.
  4. Check downstream use of funds, the affected loan/account and the current accounting period.
  5. Enter a meaningful review note of at least ten characters.
  6. Approve & Execute or Reject. Management and superusers cannot review their own reversal.
  7. Verify final status. If Executed, retain the permanent REV-000001-style reference and print the case for the reconciliation file.

What execution preserves

The original source is retained. Receipt amounts, dates, references and allocations remain evidence. Original journals remain posted, with a link to an equal opposing entry. Offsets are dated on approval in the current open accounting period, preserving the original period's recorded history.

A permanent reversal record stores source type/ID, amount, reason, evidence reference, requester approval relationship, source snapshot, effective date, approving administrator and linked offsets. Reversed evidence cannot be edited or deleted through normal model/admin operations.

Atomic execution and failure

Approval locks and revalidates the source and its postings. If the source or ledger changed after submission, execution fails and requires a fresh request based on the updated evidence. A closed current period, unbalanced source posting, invalid component allocation or downstream dependency also prevents execution. Financial changes roll back together; the approval retains a Failed outcome for investigation.

Only one pending request is allowed for a source. Only one completed reversal can exist for it. Repeated execution cannot duplicate its effect. A borrower cannot request or execute reversals; agents can request only eligible lending sources within their active portfolio scope.

Withdrawal, rejection and replacement

The requester may withdraw a pending case; it becomes Cancelled. A different administrator may reject it with a note; no financial effect occurs. Failed, rejected and cancelled cases remain review evidence. After an executed reversal, enter any legitimate corrected transaction separately with a cross-reference. A reversal journal cannot itself be reversed through this workflow.

Verify the result

  • The case is Executed with a permanent reference and review timeline.
  • The original source is visible and marked reversed/void/cancelled as applicable.
  • The related balance changes once, by the expected amount and components.
  • Existing postings have matching offsets in the current open period.
  • A linked provider collection is cancelled and its provider receipt remains reserved.
  • The customer statement and audit history explain the original and reversal movements.

Direct reversal does not cover loan disbursements, asset disposals, settled invoices/bills or arbitrary linked operational journals. These need management reconciliation using the correct business process.

Analytics versus formal reports

Loan analytics, monthly analytics, borrower analytics, workforce analytics and portfolio detail support operational exploration. Balance and activity definitions

Current-book balances and selected-period activity answer different questions. Aging and PAR

Portfolio aging measures the first scheduled repayment amount not fully covered by applied receipts and approved deposit applications. Daily and weekly schedules must use their correct due periods. Pending collections and held security do not become repayments until the applicable verified application occurs.

MCAG-style outputs follow the implementation's reporting layout; confirm the current external reporting requirements and company's classifications before filing.

29. Backups, restoration and power-cut recovery

What a complete backup contains

  • Database, including users, loans, receipts, credit, deposits, accounting, approvals, reversal cases and audit history.
  • Public company uploads and private borrower/workforce uploads.
  • Matching project source/dependency/migration release.
  • Protected environment and web-server/WSGI configuration.
  • Checksums, backup time, operator, storage location and restoration verification record.

A source ZIP is not a customer database backup. A database export usually records file paths but does not embed the corresponding uploaded images. Static output can be rebuilt; unique uploads cannot.

Application export screen

  1. Open /settings/database-backup/ as an administrator.
  2. Review the selected database scope and model/table overview.
  3. Choose the appropriate format and download.
  4. Store it in protected backup storage; it can contain identity information and password hashes.
  5. Record date, scope and format, and verify that the file is readable.
FormatPurpose and limit
JSON / XMLDjango structured model snapshots. Restore requires compatible schema, dependency order and a tested fixture procedure.
CSV ZIPOne CSV per model plus manifest; useful for review. It is not an automatic complete Django restore.
ExcelWorkbook for authorized analysis; not a native disaster-recovery image.
SQLApplication-generated table schema/inserts. Rehearse compatibility; prefer native database tools for full operational recovery.

The export helper iterates models; it does not establish one global transactional snapshot of all concurrent changes. Pause financial writes for a coherent application export or use an appropriate native snapshot procedure.

SQLite backup example

For a stopped application with no other writers, copy the database to protected storage. A simple file copy during active writes is unsafe, especially if journal/WAL files are involved. Python's SQLite backup API can produce a database copy; match your configured path and ensure a complete business cutoff.

umask 077
mkdir -p backups/private
# Stop application writers before this simple file-copy procedure.
cp db.sqlite3 backups/private/sqlite-before-update.sqlite3
sha256sum backups/private/sqlite-before-update.sqlite3

MySQL native backup example

Use a permitted account and database name. Prompt for the password or use a protected client configuration; do not put the password in the command line. Check native-tool version and privileges for the host. The example assumes transactional tables and writes paused for the business cutoff.

mysqldump --host=DB_HOST --user=DB_USER --password \
  --single-transaction --no-tablespaces \
  'YOUR_USERNAME$sikafriend' \
  --result-file=backups/private/database-before-update.sql
sha256sum backups/private/database-before-update.sql

Check the tool's exit status and validate that the dump completed. A file existing or having a large size does not prove restoration will succeed. Encrypt/copy protected backups to the organization's independent storage according to policy.

Restore rehearsal

  1. Use a separate environment and database, with external messaging/callback traffic disabled.
  2. Install the matching source and dependencies.
  3. Restore the native database backup; do not import it over an active production database.
  4. Restore public and private uploads in their corresponding protected locations.
  5. Apply only the reviewed migration path and run Django checks.
  6. Verify model counts, customer IDs, loans, receipt cash/components, credit, security and payroll.
  7. Check trial balance, active/offset journal pairs, approval cases and statements.
  8. Run the read-only integrity audit; explain every finding.
  9. Record recovery time, missing dependencies and results.

After a sudden power cut

  1. Check disk capacity, filesystem health and database startup logs before restoring anything.
  2. Preserve the current database/files and logs; do not overwrite the only copy.
  3. Determine the last verified business action using receipt, approval and audit references.
  4. Check whether the interrupted request is Pending, Executed or Failed and whether a linked record exists.
  5. Reconcile cash received independently of screen messages.
  6. Run the integrity audit and inspect affected statements/ledger entries.
  7. Resume writes only when the database and affected business evidence are coherent.
  8. Restore from a tested backup only if necessary, with management/finance reconciliation of entries after the backup cutoff.

Atomic approval execution helps prevent partial financial updates, but it cannot replace durable database storage, operating-system health, power protection or tested backups.

Financial implementation rules

  • Use Decimal values for money; validate positive finite inputs and cent precision.
  • Keep agreed loan terms separate from receipts and held customer funds.
  • Exclude pending, void and reversed effects from current financial totals.
  • Preserve original transaction evidence; correct through authorized offsets and replacement records.
  • Use atomic transactions and consistent lock ordering, commonly Loan before Payment.
  • Revalidate source state at execution time instead of trusting an old form preview.
  • Run external notifications after successful database commit where applicable.
  • Keep provider receipt reservation even after reversal.
  • Use operational source workflows for their journals.

Performance patterns

Dashboard helpers annotate/group settled receipt and deposit totals and reuse fetched records. Portfolio overview calculates summaries without loading every register; detailed exports retain full data. Related officers/users and customer IDs are prefetched or selected together. Deposit totals separate collection/application/refund sums from independent transfer sums to avoid joined-row multiplication.

When changing a template, inspect whether a property triggers database work per row. Prefer prepared view context and shared aggregate helpers. Compare query counts with representative large fixtures and verify values as well as speed. A faster total that multiplies deposits across receipts is incorrect.

Formatting rules

  • Keep identifiers as text in spreadsheets so leading zeros and permanent references are preserved.
  • Use ISO dates such as 2026-10-12 where the module expects dates.
  • Use plain numeric money values such as 1200.00, without currency symbols or grouping commas unless the parser explicitly supports them.
